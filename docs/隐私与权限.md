# 隐私与权限（2026-10-02）

案例库使用独立 `case-display-v1` 授权，诊疗照片授权不能替代展示授权。患者本人确认当前文案及图片，修改清除授权/审核，撤回停止后续公开读取；主管维护发布，授权院区在岗医生审核，护理/客服/运营无案例后台权限。见 [案例库接口与验收](案例库接口与验收.md)。

## 隐私说明与同意

- 当前版本：`2026-10-02.v1`；公开接口 `GET /api/v1/privacy-policy` 返回标题、版本、正文、生效日期和 `draft` 状态。此正文是试点草案，不代表正式合规验收。
- 患者“我的资料”展示完整正文、当前同意状态及历史记录；同意按钮需再次明确确认，无默认勾选。同意或撤回调用 `POST /api/v1/me/privacy-consent`；查询调用 `GET /api/v1/me/privacy-consent`。
- `privacy_consent_events` 追加保存患者 ID、协议版本、正文快照、动作、来源和服务端时间。按患者行锁串行化，同版本连续相同动作幂等；撤回、再次同意形成新记录，不覆盖历史。接口身份取自患者会话，不接受指定其他患者的查询参数。
- 客户端提交的版本必须与当前版本一致；旧版本返回 `409 PRIVACY_VERSION_CHANGED`。发布新版本须同时变更版本号与正文，不得只替换正文；旧同意记录保留当时正文快照，当前状态要求重新同意新版本。
- 修改姓名、授权手机号、提交预约、上传诊疗/随访照片及提交随访前，服务端验证当前版本同意。缺少同意或已撤回返回 `403 PRIVACY_CONSENT_REQUIRED`；客户端展示正文、保存用户明确同意，再以原身份和原预约幂等键重试一次。拒绝同意或中途切换身份，不保存同意、不重试原提交。
- 隐私同意、账号手机号授权、预约诊疗照片授权彼此独立。撤回隐私同意不自动删除历史诊疗记录，也不替代手机号或照片授权的撤回；撤回接口、取消预约、退出和本人历史查询不被隐私同意门禁阻断。
- 上线前由院方补齐并审核服务主体、具体保存期限、隐私联系方式、删除/导出申请流程及微信隐私指引；本次未实现法务审批或后台协议发布工作台。

## 角色和操作矩阵

所有患者资料与业务操作均先限制在员工授权院区内；医生、护理再叠加本人负责的预约或任务。前端隐藏入口只用于体验，后端接口白名单与数据查询独立鉴权。

| 角色 | 可见数据 | 可执行操作 | 禁止事项 |
| --- | --- | --- | --- |
| 医生 `doctor` | 本人主诊或承担随访的预约、患者资料、授权照片与方案；本人承担的随访任务；本人记录的问诊 | 主诊预约的方案草稿/发布、实际治疗/更正；负责患者在对应主诊院区的问诊；本人随访回评、异常处理与接手确认 | 管理员工、排班、改派；确认/拒绝预约；修改其他医生的方案与治疗 |
| 护理 `nurse` | 本人负责随访所关联的患者、预约、方案与授权照片；本人任务 | 本人随访回评、异常处理及交接接收确认 | 新增问诊、修改或发布方案、记录/更正治疗、管理账号和排班、审核预约、改派任务 |
| 客服 `customer_service` | 授权院区预约的联系人姓名、手机号、排班与到院备注；有预约关联的患者基础目录 | 确认/拒绝授权院区的待确认预约；查询预约 | 患者完整临床档案、病史、问诊、治疗、方案、照片、随访及员工管理 |
| 运营 `operations` | 授权院区的预约总数、待确认数、随访任务总数；公开院区/医生/排班介绍 | 只读运营概览 | 患者身份、手机号、预约/诊疗明细、照片、随访内容及所有业务写操作；没有导出入口 |
| 主管 `manager` | 授权院区患者与业务资料、完全处于自身院区管理范围内的员工账号 | 院区内预约审核、排班、员工开通/停用/重置密码/院区授权、随访改派/交接；保留现有演示版临床管理能力 | 跨授权院区读写或授予自己无权管理的院区；操作不完全处于自己管理范围内的员工账号 |
| 旧医护 `clinician` | 兼容存量账号，仍按关联人员及院区限制 | 主诊关系校验限制方案与治疗；本人任务回评；新增问诊需主诊关系 | 新开通账号建议明确选择医生/护理，旧角色不作为跨院区或无关联人员的兜底权限 |

医生、护理必须绑定与角色一致的随访人员。临床资料照片仍需患者独立照片授权；关联预约不等于可以绕过照片授权。运营汇总仅包含计数，不包含患者维度或联系方式，不提供任意查询参数。

## 院区鉴权

- 员工账号 `clinic_ids` 为明确院区集合；会话验证每次读取最新员工账号，客户端传入的院区筛选不扩大权限。没有授权院区默认不可访问患者业务数据。
- 预约所属院区从排班 `slots.clinic_id` 解析；任务与照片沿预约关联判定，而非信任请求中的院区 ID。列表、总数、患者聚合档案、运营概览、交接列表及照片下载均应用同一院区边界；单条越权返回不存在/无权访问，减少资源枚举。
- 排班修改、预约审核、方案/治疗、任务回评与改派、交接跟进和接收确认均检查资源范围。批量离岗交接涉及无权院区时整批拒绝；正式请求的接手人必须有有效临床账号且获授权任务所属院区。
- 人员离岗/返岗及人员事件同样要求具备其全部院区管理权限；影响所有院区的共享交接超时设置仅允许获授权全部现有院区的主管修改。
- 员工管理要求目标账号全部授权院区属于操作者权限集合；主管只能授予自己的授权院区。新增账号必须选择院区；变更使用账号版本号防止覆盖，追加 `clinics-updated` 审计事件，并立即撤销目标员工全部会话。
- 问诊记录新增独立 `clinic_id`。新问诊显式选择院区或仅在唯一可判定院区时自动归属；读取同时限制院区与记录人。迁移仅为有唯一预约院区的旧问诊回填，多院区归属不明确的记录保留但不暴露，须院方确认后补录归属。

## 迁移和验收

- 迁移 `00016_privacy_and_clinic_permissions.sql` 增加院区集合、角色、问诊归属与隐私记录。存量主管获得迁移时已存在院区；存量医生按医生资料回填；未能判定院区的旧护理账号保留账号但默认没有资料权限，须主管显式授权。后续新增院区不会自动授予现有账号。
- 迁移 `00017_clinic_assignment_audit.sql` 扩充院区变更审计动作；回滚该迁移不缩窄审计枚举、不删除院区变更历史，以保留已生成的记录。
- 部署时先执行迁移 16、17，再启动新版 API。已有未同意的患者首次提交资料会提示阅读当前说明；现有账号不自动伪造同意。
- 回归覆盖：角色白名单、护士临床写入拒绝、客服/运营敏感接口拒绝、未知接口默认拒绝、版本冲突、本人记录查询、隐私提交门禁、可独立撤回；客户端同意后保留原幂等键、拒绝不提交、切换身份不误记同意；真实 MySQL 验证记录幂等/正文快照/撤回及跨院区预约查询、审核、排班修改、汇总隔离。
- 正式患者、微信真机、生产图片存储与院方实际权限分配仍需独立验收。
